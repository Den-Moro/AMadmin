# Инструкция для администратора

Руководство по эксплуатации AMadmin: как поднять сервер, пользоваться админ-панелью и
раскатать клиент на кассы. Полное техническое ТЗ и архитектурные решения — в
[AGENTS.md](AGENTS.md); текущий статус разработки — в [README.md](README.md). Инструкция
для сотрудников магазина — в [INSTRUCTIONS.md](INSTRUCTIONS.md).

## 1. Что это за система

Два больших модуля:

1. **Оповещения** — сервер (PHP + SQLite) рассылает уведомления о плановых/срочных
   IT-работах на ПК магазинов; клиент (PowerShell + WPF) показывает их и подтверждает
   получение. Реализовано и проверено.
2. **Удалённое администрирование** — управление службами, диспетчер задач, файлы,
   скрипты на кассах массово. Управление службами реализовано и проверено; остальное —
   по плану, отдельными шагами (см. известные ограничения).

## 2. Сервер

### 2.1 Запуск через Docker (рекомендуется для теста/разработки)

```bash
docker compose up -d --build
```

Миграции (`server/migrations/`) накатываются автоматически при каждом старте контейнера
через `server/bin/migrate.php` — идемпотентно, не только на первом запуске: безопасно
запускать и на пустом томе, и на уже существующей БД с новыми миграциями поверх старых.
Сервер слушает `http://localhost:8000`.

Тестовые данные и первый логин в панель (если ещё не созданы):

```bash
docker compose exec server php -r "(new PDO('sqlite:/app/data/amadmin.sqlite'))->exec(file_get_contents('/app/dev-seed.sql'));"
docker compose exec server php bin/create-admin.php <логин> <пароль>
```

### 2.2 Запуск напрямую (без Docker)

См. раздел "Быстрый старт (сервер)" в [README.md](README.md). Продакшен по плану —
ручная установка на Windows-хосте (IIS/Apache), Docker — только для тестирования.

### 2.3 Логи и диагностика

- Серверный лог: `server/logs/app.log` (в Docker — `docker compose exec server tail -f logs/app.log`).
- Уровень логирования настраивается в `config.php` (`log_level`: `debug`/`info`/
  `warning`/`error`). Пока приложение в бете — держите `debug`, это значение по умолчанию.
- Клиентские логи — по одному файлу на каждый процесс агента: `client/ui-agent.log`
  (UI-агент) и `client/management-agent.log` (агент управления), тот же принцип уровней
  (`config.json` → `log_level`).

## 3. Админ-панель

Откройте `http://<адрес-сервера>/admin/login.html`. Логинов с самого начала может быть
несколько — заводятся через `server/bin/create-admin.php`, публичной регистрации в
панели нет и не будет. После 5 неудачных попыток подряд логин временно блокируется.

### 3.1 Дашборд (`index.html`)

Список ПК: магазин, `hostname\username`, тип устройства, онлайн/офлайн (по времени
последнего опроса), когда последний раз выходил на связь. Поиск и фильтры по магазину/
типу устройства.

### 3.2 Оповещения (`notifications.html`)

Форма создания: текст, важность (важное всегда принудительное окно; неважное — по
настройке клиента), размер окна, кому (всем / конкретному магазину / группе хостов /
типу устройства / конкретному ПК), и опционально мануал — либо выбрать готовый из
библиотеки (текст скопируется в поле), либо вписать вручную. Ниже — история уже
отправленных оповещений со сводными счётчиками показов/подтверждений.

Повторяющиеся оповещения (ежедневно/еженедельно) и функция "догона" пропущенных пока не
реализованы в панели — см. известные ограничения ниже.

### 3.3 Группы хостов (`groups.html`)

Свои произвольные группы ПК, не привязанные к структуре "магазин" (например "Кассы 1
этажа"). Группа создаётся, затем через неё же добавляются/убираются конкретные ПК.
Группа становится доступна как цель рассылки сразу после создания.

### 3.4 Библиотека мануалов (`manuals.html`)

Инструкции (текст или ссылка) для повторного использования при создании оповещений —
создание, редактирование, удаление. Текст мануала копируется в оповещение в момент
отправки, а не связывается "вживую" — более поздняя правка мануала в библиотеке не
меняет задним числом уже отправленные оповещения.

### 3.5 Команды (`commands.html`)

Удалённое администрирование. Пока доступно только управление службами Windows: имя
службы, действие (запустить/остановить/перезапустить), таргетинг (тот же набор целей,
что и у оповещений). Перед отправкой на несколько хостов — подтверждение "точно на N
хостов?".

Небольшой список системных служб (`RpcSs`, `DcomLaunch`, `EventLog`, `Winmgmt`) нельзя
остановить/перезапустить через эту форму — проверка стоит и на сервере (при создании
команды), и в самом агенте управления (перед выполнением), см. `$protectedServices` в
`AdminCommandsController.php` и `$ProtectedServices` в `ManagementAgent.ps1`. **Список
провизорный** — пересмотрите его под свою инфраструктуру перед реальным использованием
на кассах, это явно оставлено на усмотрение реализации в исходном ТЗ.

Ниже — список последних команд со сводкой по статусам (в процессе/успех/ошибка) и кнопка
"Результаты" — детальная таблица по каждому ПК, который уже успел опросить сервер с
момента отправки команды (те, кто ещё не опрашивал, появятся там на следующем их опросе).

## 4. Клиенты

Два разных процесса на одном ПК, с разными правами (см. AGENTS.md, "два агента, не
один") — не два разных проекта, но разные точки входа и разные учётные данные запуска.

### 4.1 UI-агент (оповещения)

1. Скопировать `client/config.example.json` → `client/config.json`, указать
   `server_url` и `agent_token` конкретного ПК (сейчас токен выдаётся вручную —
   саморегистрация агента ещё не реализована, см. известные ограничения).
2. Запуск: `powershell -File client/UiAgent/UiAgent.ps1`, от имени обычного
   пользователя (не администратора/SYSTEM) — иначе окно оповещения будет не видно.

### 4.2 Агент управления (команды)

Тот же `config.json`, что и у UI-агента (один `agent_token` на ПК, не по одному на
процесс).

1. Запуск: `powershell -File client/ManagementAgent/ManagementAgent.ps1`.
2. **Обязательно от имени администратора/SYSTEM** — иначе любая команда, реально меняющая
   состояние службы, корректно завершится статусом `failed` с сообщением о нехватке прав
   (это не баг, а ожидаемое поведение: без прав Windows и не даст управлять службами). В
   проде — через задачу в планировщике с опцией "выполнять вне зависимости от входа
   пользователя" и наивысшими правами (см. AGENTS.md, "Технологический стек").

### 4.3 Массовая раскатка

Сборка в `.exe` через `ps2exe`, регистрация автозапуска через `schtasks` — по плану, ещё
не реализовано.

## 5. Известные ограничения (осознанный бэклог)

- Нет CSRF-защиты на POST-запросах админ-панели.
- Двухфакторная аутентификация для входа в панель — не реализована.
- Саморегистрация ПК (выдача `agent_token` при первом запуске агента) — пока токены
  создаются вручную.
- Повторяющиеся оповещения (`recurrence` в схеме есть, генерация по расписанию — нет) и
  режим "догона" пропущенных (`CatchUpMissed`) — не реализованы.
- CRUD для магазинов и типов устройств, экспорт статистики, история по конкретному ПК,
  пилотный режим в UI, шаблоны типовых сообщений, просмотр логов прямо из панели — пока
  нет отдельных экранов.
- Сборка `.exe` клиента и групповая раскатка — не реализованы.
- Удалённое администрирование: реализовано только управление службами. Диспетчер задач,
  файлы со сравнением по хешу, запуск произвольных скриптов — по плану, по очереди,
  отдельными шагами (скрипты — в последнюю очередь, как самая рискованная функция).
- Список защищённых служб в управлении службами — провизорный, требует ревью под
  конкретную инфраструктуру перед продом.

Актуальный чек-лист статуса — всегда в [README.md](README.md).
