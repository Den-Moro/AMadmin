# Промт для Claude Code — приложение оповещений для магазинов

Скопируйте этот текст как первое сообщение в сессии Claude Code (в папке проекта, желательно с уже инициализированным пустым git-репозиторием).

## Контекст и роль

Ты помогаешь мне (системному администратору, средний уровень в PowerShell/Bash/JS/PHP/SQL,
слабое понимание REST API) спроектировать и написать клиент-серверное приложение оповещений
для розничных магазинов. Работай итеративно: сначала предложи план файлов/структуры проекта,
дождись моего подтверждения, затем пиши код небольшими шагами с объяснением каждого шага —
я учусь по ходу дела, особенно в части API.

## Задача

Компания обслуживает магазины на аутсорсе. Кассиры и менеджеры магазинов не знают, когда
проводятся IT-работы (плановые или срочные), а администратору неудобно управлять большим
парком ПК точечно. Нужно приложение из двух больших частей:

1. **Оповещения** — показывает пользователям ПК оповещения о текущих/предстоящих работах,
   администратор рассылает их централизованно.
2. **Удалённое администрирование** — администратор может со своей панели: управлять
   службами Windows, разворачивать/заменять файлы (со сравнением по хешу), удалённо
   запускать скрипты и приложения, работать с диспетчером задач массово на выбранных
   хостах. Хосты можно группировать, искать и называть понятными именами.

Общие требования:
- имеет приятный UI/UX с обеих сторон (клиент и админ-панель);
- легко устанавливается на большое количество ПК в магазинах.

**Важно про приоритет реализации:** это два больших направления с разным уровнем риска.
Оповещения — низкий риск, можно смело делать MVP и итерировать. Удалённое администрирование
— по сути полноценный RMM-функционал (удалённое выполнение кода на десятках/сотнях ПК),
поэтому: сначала полностью доводим до рабочего состояния оповещения (см. "Порядок работы"),
и только потом переходим к удалённому администрированию отдельным этапом, с отдельным
вниманием к правам доступа и аудиту (см. соответствующий раздел ниже).

## Окружение установки

**Клиент:** ставится на кассовые ПК, где уже работает кассовое ПО "Профи-Т" и подключено
фискальное оборудование (фискальный регистратор, денежный ящик и т.п.), через которые
идёт реальная торговля. ОС: Windows 7, 10, в будущем возможен Windows 11. **Windows 7 —
жёсткое ограничение**, учитывай его при выборе любых библиотек и API: например, Electron
не подходит — начиная с версии 23 он не поддерживает Windows 7/8/8.1.

Отсюда критичное требование, которого не было в предыдущих версиях документа:
**агент не должен мешать активной транзакции на кассе.** Форсированное topmost-окно
(см. функциональные требования) не должно перекрывать экран "Профи-Т" в момент, когда
кассир находится в процессе пробития чека — иначе можно сорвать фискальную операцию
или запутать кассира прямо во время расчёта с покупателем. Практическое решение
(нужно продумать на этапе реализации, в первом приближении): агент показывает важные
принудительные оповещения только когда касса не находится в активной транзакции — но
у агента нет прямого доступа к состоянию "Профи-Т", поэтому либо ограничиваемся
эвристикой (например, не показывать поверх активного окна кассовой программы, если это
технически различимо), либо смещаем показ на ближайшую паузу (агент ждёт непродолжительное
время и повторяет попытку, если в моменте показ не удался). Это не мелкая деталь —
обсудить с Claude Code отдельно перед реализацией принудительного режима, а не просто
"показать topmost и всё".

Также агент никак не должен напрямую взаимодействовать с фискальным оборудованием —
он работает только с UI-слоем Windows, никаких COM-портов/драйверов кассового оборудования
это не касается.

**Сервер:** разворачивается вручную внутри сети компании, на хосте с Windows 10, 11
или Windows Server 2008 и новее. Windows Server 2008 — очень старая ОС (расширенная
поддержка Microsoft закончилась в 2020 году), поэтому:
- Так же, как и на кассах с Win7, может понадобиться явно включить/обновить поддержку
  TLS 1.2 на уровне ОС/веб-сервера — иначе агенты не смогут установить HTTPS-соединение
  или сам сервер не сможет исходящими запросами (если понадобятся) работать с современными
  сервисами.
- Перед стартом реализации стоит явно проверить, какая версия PHP и MySQL/веб-сервера
  (IIS или Apache) реально ставится и стабильно работает на конкретной версии Server
  2008, которая будет использоваться (обычную или R2) — современные версии PHP могут
  не поддерживаться на очень старой ОС, тогда придётся закладывать более старую, но ещё
  поддерживаемую ветку PHP.

## Деплой (как планируется)

- **Клиент:** массово, PowerShell-скриптом с ПК администратора — скрипт копирует .exe
  на кассу (например, через административную сетевую шару `\\host\C$`) и регистрирует
  автозапуск через `schtasks` (создание задачи в планировщике удалённо). Для этого
  нужны: доменные/локальные админ-права на кассах, доступ к admin$-шаре (SMB) и, если
  используется `Invoke-Command`/WinRM вместо простого `schtasks /create /s`, включённый
  WinRM на кассах. Уточнить на этапе реализации, какой именно способ доступен в вашей
  сети (WinRM часто выключен по умолчанию и требует отдельного разрешения через GPO).
- **Сервер:** ручная установка (один хост внутри сети компании) — автоматизация деплоя
  сервера не требуется.

## Технологический стек (уже согласован, не меняй без обсуждения)

**Важное архитектурное решение: два агента, не один.** Показ принудительных окон должен
происходить в сессии залогиненного пользователя (иначе пользователь их просто не увидит).
Управление службами, диспетчером задач и выполнение скриптов обычно требуют повышенных
прав — а служба Windows, запущенная от SYSTEM, работает в Session 0 и **не может показывать
окна в сессии пользователя** (Session 0 isolation, начиная с Vista/Win7). Поэтому:
- **UI-агент** — то, что уже описано ниже: работает в сессии пользователя, показывает
  оповещения, отвечает за ack/reacted.
- **Агент управления** — отдельный процесс, запущенный от SYSTEM (через задачу в
  планировщике с опцией "Выполнять вне зависимости от того, выполнён ли вход пользователя
  в систему" и наивысшими правами, либо через `PsExec`/обёртку в службу) — опрашивает
  сервер за командами (службы/файлы/скрипты/процессы) и выполняет их без участия
  пользователя и без UI.

Оба агента могут быть одним и тем же PowerShell-скриптом с разными точками входа/режимами
запуска — не обязательно два отдельных проекта, но это два разных процесса на ПК с разными
правами и разными задачами.

**Безопасность канала связи (обязательно, добавляю отдельно — без этого удалённое
администрирование нельзя выкатывать в прод):**
- Каждый ПК при первой регистрации получает уникальный `agent_token` (генерируется
  сервером, сохраняется в конфиге агента). Каждый последующий запрос от агента должен
  включать этот токен — сервер не должен принимать команды/отдавать оповещения по
  простому `pc_id` без токена, иначе любой в сети магазина, кто узнает URL API, сможет
  слать себе чужие оповещения или, хуже, читать команды управления, предназначенные
  другому хосту.
- То, что вся архитектура построена на исходящем опросе (агент сам стучится на сервер по
  HTTPS), а не на входящих подключениях к ПК — важное преимущество именно для розницы:
  не нужно пробрасывать порты или поднимать VPN до каждого магазина. Это стоит сохранить
  и для команд управления, не переходить на push/входящие соединения без крайней
  необходимости.
- Доступ в саму админ-панель, с учётом того что теперь через неё выполняется код на
  всех ПК сети, должен быть максимально защищён: строгий пароль, блокировка после
  нескольких неудачных попыток входа (защита от подбора). Двухфакторную аутентификацию
  можно отложить на будущее, но не забыть про неё в бэклоге.

**Клиентский агент**
- PowerShell + WPF (XAML) — GUI-часть через XAML (декларативно, похоже на HTML/CSS),
  логика на PowerShell.
- Сборка в один .exe через `ps2exe`.
- HTTP-запросы к серверу через `Invoke-RestMethod` (GET/POST), опрос (polling) раз в
  30–60 секунд.
- Обязательно явно включай TLS 1.2 в начале скрипта
  (`[Net.ServicePointManager]::SecurityProtocol`), иначе HTTPS сломается на Windows 7.
- Автозапуск через планировщик задач.
- Тип устройства (`device_type`: касса / ПК менеджера / ПК администратора / другое)
  задаётся в том же конфиг-файле, что и `ForceMode` — заполняется при установке/раскатке
  агента и отправляется на сервер при первой регистрации/heartbeat.
- Автоматический сбор `hostname` (`$env:COMPUTERNAME`) и текущего `username`
  (`$env:USERNAME`) — без ручного ввода. Отправляются на сервер при регистрации и при
  каждом heartbeat.
- Локальное логирование агента в файл (с ротацией/ограничением размера) — все события:
  запуск, опрос сервера, показ оповещения, ack, ошибки сети. Обязательно для дебага
  на удалённых ПК, куда не всегда есть быстрый доступ.
- .exe должен быть подписан сертификатом (code signing) — иначе Windows SmartScreen
  и антивирусы на масштабе в десятки/сотни магазинов будут постоянно блокировать
  запуск и создавать лишние обращения в поддержку.

**Сервер**
- PHP (без тяжёлых фреймворков, plain PHP + PDO) + MySQL.
- Простой REST API (GET/POST), JSON.
- Серверное логирование: все входящие запросы, ошибки, отправленные/пропущенные
  оповещения — в отдельный лог-файл или таблицу, чтобы можно было разобрать
  "почему конкретный ПК не получил оповещение".

**Админ-панель**
- Обычная веб-страница HTML5 + JS (vanilla или лёгкая библиотека, без сборщиков —
  чтобы было просто разворачивать), дёргает тот же API.

## Структура данных (отправная точка, можно уточнять по ходу)

- `stores` — магазины (плюс флаг `is_pilot` — пилотный/тестовый магазин для обкатки
  новых типов оповещений отдельно от прода)
- `pcs` — ПК (store_id, hostname, username, display_name, device_type, agent_token,
  last_seen, agent_version). `agent_token` — уникальный токен, выданный сервером при
  регистрации, обязателен в каждом запросе агента (см. раздел про безопасность канала
  связи выше). `display_name` — понятное имя хоста, которое администратор задаёт сам
  (например "Касса 1" вместо голого hostname) и которое приоритетно показывается в UI,
  но не заменяет технический `hostname`/`username`, которые всё равно нужны для
  идентификации и дебага. `username` — имя пользователя Windows, под которым сейчас
  залогинен агент (берётся автоматически, не вводится вручную) — вместе с `hostname` даёт
  понятную идентификацию вида "hostname\username" в списках и истории, а не голый ID ПК.
  `device_type` — классификация устройства (например: касса, ПК менеджера, ПК
  администратора магазина, другое) — нужна для точечной рассылки оповещений не только
  на кассы, но и, например, только на администраторские ПК.
- `host_groups` — id, name (произвольные группы хостов, не привязанные к структуре
  "магазин", например "Кассы 1 этажа" или "Проблемные хосты").
- `host_group_members` — group_id, pc_id (ПК может состоять в нескольких группах).
- `notifications` — определение оповещения (шаблон/правило): id, text, priority
  (важное/неважное), manual_url (опционально), created_by, size (small/medium/large),
  recurrence (null/once, daily, weekly, custom-интервал)
- `notification_occurrences` — конкретный "показ" оповещения: id, notification_id (FK),
  fire_at (когда именно этот показ должен произойти). Для обычного разового оповещения
  создаётся ровно одна запись сразу. Для повторяющегося (`recurrence` != once) сервер
  по расписанию (например, cron-задача) генерирует новую запись на каждый следующий
  повтор. Всё, что относится к конкретному разу показа (подтверждения, статус доставки),
  привязывается именно к occurrence, а не к самому `notifications` — иначе после первого
  ack повторяющееся оповещение считалось бы подтверждённым навсегда.
- `notification_targets` — notification_id, target_type (all/store/group/pc/device_type),
  target_id (цель одна и та же для всех повторов оповещения)
- `notification_acks` — occurrence_id (не notification_id), pc_id, acked_at,
  reacted (bool, опционально)
- `manuals` — id, title, url_or_text, created_at, updated_at (библиотека мануалов
  для повторного использования)
- `commands` — команда удалённого администрирования: id, type (service_control /
  file_deploy / script_run / process_action), payload (JSON — детали конкретного типа,
  например имя службы и действие start/stop/restart, или путь+хеш файла, или текст/путь
  скрипта и аргументы, или имя/PID процесса и действие), target_type
  (pc/group/store/device_type/all — тот же набор, что и у `notification_targets`, чтобы
  не путаться), target_id, created_by, created_at.
- `command_results` — command_id, pc_id, status (pending/in_progress/success/failed/
  timeout), output (stdout/stderr/exit code или сообщение об ошибке), claimed_at,
  executed_at. Один `commands` может выполняться на многих хостах сразу — статус и
  результат у каждого хоста свои (по аналогии с тем, как `notification_acks` разведён
  с самим оповещением). Статусы `pending → in_progress → success/failed/timeout` нужны
  для идемпотентности: агент должен сначала пометить результат как `in_progress`
  (застолбить), и только потом выполнять — если он упадёт после выполнения, но до
  отправки финального статуса, при следующем опросе он увидит "уже in_progress" и не
  выполнит одну и ту же команду (например, рестарт службы или запуск скрипта) дважды.

Логика "догона" (опционально, управляется конфиг-параметром `CatchUpMissed = On|Off` —
как и `ForceMode`, чтобы было легко включать/выключать без пересборки): если включено,
клиент при каждом запуске/восстановлении сети запрашивает у сервера все важные
occurrence за последние N часов, на которые ещё нет ack от этого pc_id, а не только те,
что активны прямо сейчас.

## Интерфейс настроек (администратор)

Отдельный раздел админ-панели "Настройки" — чтобы конфигурировать поведение системы
без правки кода и без похода на каждый ПК вручную.

**Доступ:**
- Вход в саму админ-панель — по логину/паролю (отдельно от пароля на клиентском агенте,
  это разные вещи). На старте достаточно одной учётки администратора, но таблицу
  пользователей панели закладывать сразу с расчётом на несколько логинов.

**Настройки по умолчанию (применяются к новым оповещениям, если не переопределены при
создании конкретного оповещения):**
- `ForceMode` по умолчанию для неважных оповещений (Strict/Soft).
- Длительность таймера до активации кнопки закрытия (сейчас 30 секунд — сделать
  настраиваемым числом, а не константой в коде).
- `CatchUpMissed` — включён/выключен догон пропущенных оповещений по умолчанию.
- Размер окна по умолчанию (маленькое/среднее/крупное).
- Брендинг: название IT-компании и контакт для связи, отображаемые в окне у клиента.

**Справочники (свои CRUD-экраны, не просто константы в коде):**
- Магазины — добавление/редактирование, включая флаг `is_pilot`.
- Типы устройств (`device_type`) — список редактируется тут же, а не хардкодится
  (например, чтобы потом добавить "ПК склада" без правки кода).
- Библиотека мануалов — то же самое место, где мануалы создаются/редактируются при
  создании оповещения (см. функциональные требования выше), плюс отдельный полный
  список для наведения порядка (архивировать неактуальные и т.п.).
- Шаблоны типовых сообщений — создание/редактирование/удаление.

**Управление паролем клиента:**
- Смена общего пароля, который защищает действия на стороне клиентского агента
  (выход из автозагрузки, изменение конфига и т.д.) — с этого экрана, без ручного
  редактирования конфиг-файлов на каждом ПК. Как именно новый пароль доедет до всех
  агентов (при следующем опросе сервера) — решить на этапе реализации.

**Прочее:**
- Версия агента, которая считается актуальной, и список ПК с устаревшей версией —
  полезно, когда будет реализовано автообновление.

## Функциональные требования

**Клиент:**
- Окно оповещения открывается принудительно поверх всех окон (topmost, без возможности
  свернуть/уйти в фон программным путём) — расчёт на не самого технически подкованного
  пользователя, оповещение не должно теряться за кассовой программой. **Важно:** с учётом
  того, что это касса с "Профи-Т" и фискальным оборудованием — см. предупреждение в разделе
  "Окружение установки" про недопустимость показа поверх активной транзакции.
- Закрыть окно можно только через встроенную кнопку, и кнопка становится активной не раньше
  чем через 30 секунд после появления (таймер видимого обратного отсчёта на самой кнопке) —
  это гарантирует, что пользователь не закроет не глядя.
- Классификация сообщений: важное / неважное. Важные — всегда принудительный topmost-режим
  с 30-секундным таймером на кнопке. Для неважных режим показа управляется конфиг-параметром
  клиента (например, `ForceMode = Strict | Soft`): `Strict` — то же принудительное окно,
  `Soft` — немодальное окно в углу экрана без блокировки. Переключатель нужен для удобного
  тестирования обоих сценариев без пересборки — задать через простой конфиг-файл рядом
  с .exe (например, JSON или INI), который агент читает при старте.
- Если для оповещения указан мануал (ссылка или текст простой инструкции) — показываем его
  прямо в окне или кнопкой "Инструкция", если требуются действия от пользователя. Важно:
  если мануал есть, кнопка закрытия окна должна оставаться неактивной, пока пользователь
  не откроет мануал хотя бы один раз (в дополнение к таймеру 30 секунд) — это не должно
  быть тем, что можно пропустить.
- Опционально: отслеживание реагирующих пользователей — помимо факта "закрыл окно" (ack),
  можно фиксировать явное "я сделал/понял" через отдельную кнопку (`reacted`), чтобы отличать
  формальное закрытие от осознанного подтверждения. Пометить как необязательную фичу для
  поздней итерации.
- Иконка в трее с историей последних оповещений.
- Режим "не беспокоить" вне рабочих часов не действует на важные оповещения — они всё равно
  показываются принудительно.
- В окне оповещения — небольшой брендинг: название обслуживающей IT-компании и контакт
  для связи, чтобы пользователь понимал, кто это шлёт и куда обращаться при вопросах.
- Защита паролем: любые действия, которые обычный пользователь магазина не должен делать
  сам (выход агента из автозагрузки, попытка закрыть/убить процесс через свою же кнопку
  в трее, изменение конфиг-параметров вроде `ForceMode`/`device_type`) — должны требовать
  пароль. Пароль общий (задаётся в конфиге при установке) или хранится хэшем локально —
  цель не криптостойкость, а простая защита "от шаловливых рук", не более.

**Админ-панель:**
- Дашборд: какие ПК онлайн/офлайн (по last_seen), когда последний раз выходили на связь.
- Список подключённых ПК прямо на дашборде — таблица с магазином, идентификацией вида
  `hostname\username` (текущий залогиненный пользователь), типом устройства, статусом
  (онлайн/офлайн), последним временем на связи; с фильтром по магазину/типу устройства
  для быстрого поиска.
- Выгрузка статистики пользователей (CSV/Excel): по ПК/магазину — количество полученных
  оповещений, подтверждений (ack), явных реакций (reacted), среднее время реакции —
  для отчётности и разбора проблемных точек без ручного копирования из таблиц.
- Форма создания оповещения: текст, классификация (важное/неважное), время, цель
  (все/магазин/группа/ПК/тип устройства — например, только кассы или только
  администраторские ПК), опциональная ссылка на мануал, размер окна (маленькое/среднее/
  крупное), а также опция сделать оповещение регулярным (повторять ежедневно/еженедельно/
  по своему интервалу) — для напоминаний вроде плановой сверки или регламентных работ.
- Таблица подтверждений по каждому оповещению (кто закрыл, и опционально — кто явно
  отреагировал).
- Шаблоны типовых сообщений.
- Библиотека мануалов: возможность сохранять и дополнять инструкции (текст или ссылку),
  чтобы при повторяющейся ситуации не писать их заново, а выбирать из списка при создании
  оповещения.
- История по конкретному ПК: не только "кто подтвердил это оповещение", но и полный список
  оповещений, которые получал данный ПК за период — полезно при разборе жалоб
  "мне никто не сказал".
- Пилотный режим: возможность пометить магазин как `is_pilot` и рассылать туда тестовые
  оповещения отдельно от прода, для обкатки новых типов сообщений перед массовой рассылкой.
- Просмотр логов (клиентских и серверных) прямо из админ-панели или хотя бы понятная
  инструкция, где их искать — это должно быть предусмотрено с самого начала, а не
  прикручено потом.

## Удалённое администрирование (новый функционал)

Выполняется агентом управления (см. архитектурное решение выше), не UI-агентом.
Обмен командами — тот же принцип, что и с оповещениями: агент управления опрашивает
`GET /commands` (свои, ещё не выполненные), выполняет, репортит результат через
`POST /commands/{id}/result`.

**Управление службами (Win 7, 10, 11):**
- Получение списка служб хоста (`Get-Service`) с состоянием (running/stopped/etc.).
- Действия: старт/стоп/рестарт конкретной службы (`Start-Service`/`Stop-Service`/
  `Restart-Service`) — стандартные cmdlet'ы, доступны из коробки на всех целевых ОС.
- Защита от массовой ошибки: небольшой список критичных системных служб (например,
  сама служба, отвечающая за агент управления, и явно системные вроде RPC), которые
  нельзя остановить через это средство, даже случайно — конкретный список согласовать
  на этапе реализации.

**Управление файлами со сравнением по хешу:**
- Администратор указывает файл (загружает на сервер или даёт путь) и целевой путь на ПК.
- Агент считает хеш локального файла (`Get-FileHash -Algorithm SHA256`), сравнивает
  с хешем эталонного файла с сервера — заменяет, только если хеши различаются
  (экономит трафик и не трогает файл лишний раз, если он и так актуален).
- Перед заменой агент сохраняет копию текущего файла (например, с суффиксом `.bak` и
  датой) — чтобы можно было откатиться вручную, если новый файл окажется проблемным.
- Результат (заменён/пропущен — совпадает/ошибка) уходит в `command_results`.

**Удалённый запуск скриптов и приложений:**
- Команда содержит текст скрипта (PowerShell/CMD) или путь к уже лежащему на ПК
  исполняемому файлу, плюс аргументы.
- Агент выполняет с явным обходом Execution Policy для полученных скриптов
  (`-ExecutionPolicy Bypass` для конкретного запуска, не менять политику глобально на
  ПК), захватывает stdout/stderr/код возврата, отправляет в `command_results`.
  Долгие/интерактивные скрипты не поддерживаем в первой версии — синхронный запуск
  с таймаутом.

**Диспетчер задач, массово на выбранные хосты:**
- Получение списка процессов хоста (`Get-Process`).
- Завершение процесса по имени/PID (`Stop-Process`), с возможностью выбрать сразу
  несколько хостов и применить действие ко всем сразу (одна команда → много
  `command_results`, по одному на хост).
- Защита от массовой ошибки: чёрный список критичных системных процессов (`explorer`,
  `csrss`, `winlogon`, сам процесс агента и т.п.), которые нельзя завершить через это
  средство — иначе один неверный клик способен положить explorer.exe на сотне касс
  одновременно.

**Группировка, поиск и именование хостов:**
- Хосты можно объединять в произвольные группы (`host_groups`), независимо от привязки
  к магазину — группа может быть таргетом и для оповещений, и для команд управления.
- Поиск хостов в админ-панели: по `display_name`, `hostname`, `username`, магазину,
  группе, типу устройства — одно поле поиска с фильтрами.
- Администратор может задать читаемое имя (`display_name`) любому хосту — оно
  используется везде в UI вместо голого hostname, но техническое имя остаётся доступным.

**Безопасность и аудит (обязательно, не опционально — это удалённое выполнение кода
на десятках/сотнях ПК):**
- Каждая команда обязательно логируется: кто из администраторов её создал, когда, какой
  тип, на какие хосты, с каким результатом — без возможности отключить это логирование.
- Список последних команд с результатами должен быть доступен на самой странице
  удалённого администрирования, а не только в сырых логах.
- Подтверждение перед отправкой массовой команды на много хостов сразу (простое
  "точно на N хостов?" в UI) — это не заменяет аудит, но снижает шанс случайной ошибки.

## UX (отдельно, чтобы не растворялось в функциональных требованиях)

**Клиентская сторона (пользователь магазина):**
- Минимум когнитивной нагрузки: крупный понятный текст, минимум кнопок, явный визуальный
  сигнал важности (цвет/иконка), не нужно ничего "разбираться" — один взгляд и всё понятно.
  Ориентир — не самый технически подкованный пользователь.
- Принудительный режим не должен пугать/выглядеть как ошибка или вирус — спокойный,
  фирменный стиль, брендинг компании, понятный текст "почему это окно нельзя сразу закрыть".
- Обратный отсчёт на кнопке должен быть визуально очевиден (прогресс-бар/цифры), а не
  просто неактивная серая кнопка без объяснений.
- Мануал/инструкция открывается в один клик, без необходимости искать её где-то ещё.

**Серверная сторона (администратор):**
- Форма создания оповещения — максимально быстрая (создать и отправить типовое оповещение
  должно занимать секунды, а не минуты): шаблоны и библиотека мануалов должны сокращать
  ввод, а не требовать каждый раз печатать заново.
- Дашборд должен сразу давать ответ на вопрос "всё ли доставлено и все ли увидели" без
  необходимости лезть в отдельные логи для рутинных случаев.
- Логи и история — доступны, но не мешают основному рабочему процессу (создание/мониторинг
  оповещений); лишняя техническая информация не должна быть на первом экране.

## Пользовательские сценарии

**Сценарий администратора:**
1. Заходит в админ-панель, видит дашборд: какие ПК онлайн/офлайн, по магазинам.
2. Узнаёт о предстоящих или текущих IT-работах (из своей тикет-системы или напрямую).
3. Нажимает "Создать оповещение": выбирает готовый шаблон или пишет текст заново.
4. Указывает важность (важное/неважное), время (сейчас или запланировано), цель рассылки
   (все / конкретный магазин / группа магазинов / тип устройства, например только кассы).
5. При необходимости прикрепляет мануал — выбирает существующий из библиотеки или создаёт
   новый (текст/ссылку), который тут же попадает в библиотеку для повторного использования.
6. Отправляет оповещение, дальше наблюдает статус подтверждений в реальном времени
   (кто закрыл окно, кто явно отреагировал, кто ещё не видел).
7. Если магазин помечен как пилотный — сначала гоняет новый тип сообщения только там.
8. После завершения работ отправляет короткое оповещение "работы завершены" (тоже
   из шаблона).
9. При разборе жалобы вида "мне никто не сказал" — открывает историю конкретного ПК
   и видит, какие оповещения приходили и что с ними стало; при необходимости смотрит
   серверные логи прямо из панели.

**Сценарий пользователя магазина (кассир/менеджер):**
1. Работает как обычно в кассовой/учётной программе.
2. Внезапно поверх всех окон появляется оповещение — если оно важное, окно принудительное
   и его нельзя свернуть или переключиться в фон.
3. Видит крупный понятный текст, цвет/иконку важности и, если админ указал, брендинг
   компании с контактом для связи.
4. Если оповещение требует действий — видит кнопку "Инструкция", открывает мануал в один
   клик, выполняет шаги.
5. Кнопка закрытия окна неактивна первые 30 секунд — пользователь видит обратный отсчёт
   и понимает, что окно закроется само, как только время выйдет.
6. Нажимает "Понятно" (и опционально отдельную кнопку "Я выполнил", если требовалось
   действие) — подтверждение уходит на сервер.
7. Продолжает работу; при желании открывает иконку в трее, чтобы посмотреть историю
   последних оповещений.
8. Если включён режим догона (`CatchUpMissed`), и ПК был выключен или без сети в момент
   рассылки — при следующем включении агент сам подтягивает пропущенные важные
   оповещения и показывает их.
9. Если пользователь пытается закрыть агент, снять его из автозагрузки или изменить
   настройки — система запрашивает пароль, обычному пользователю это недоступно.

## Порядок работы (следуй этим этапам, не забегай вперёд)

1. Предложи структуру проекта (папки/файлы) для сервера и клиента отдельно.
2. Разверни минимальную схему MySQL (миграция/SQL-файл) под таблицы выше.
3. Реализуй 2 базовых эндпоинта сервера: `GET /occurrences` (активные для конкретного ПК)
   и `POST /occurrences/{id}/ack`. Даже в MVP без функции повторов заводи их сразу через
   occurrence — на разовое оповещение просто создаётся одна запись, зато не придётся
   потом переделывать схему и API под повторяющиеся оповещения.
4. Реализуй минимальный PowerShell-клиент: опрос эндпоинта, показ простого WPF-окна,
   отправка ack.
5. Только после того как MVP клиент-сервер работает — переходи к админ-панели,
   таргетингу, приоритетам и дашборду.
6. Доводи оповещения до полного функционала из раздела "Функциональные требования"
   (мануалы, размер, повторы, группы, догон и т.д.) — прежде чем начинать удалённое
   администрирование.
7. Только после этого — отдельным этапом: агент управления (SYSTEM), эндпоинты
   `GET /commands` / `POST /commands/{id}/result`, и по очереди функции из раздела
   "Удалённое администрирование": сначала службы (проще всего), потом диспетчер задач,
   потом файлы с хешем, и в последнюю очередь — запуск произвольных скриптов (самая
   мощная и самая рискованная функция, к ней — обязательный аудит с самого начала).
8. В конце — инструкция по сборке .exe через ps2exe и по массовому развёртыванию
   через групповые политики (GPO startup script), для обоих агентов.
